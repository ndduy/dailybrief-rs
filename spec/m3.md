# Spec: M3 — ratings, the Curator, and the approval queue

Milestone spec derived from `SPEC.md` §5 (Curator), §6 (feedback), §8 (M3 row) and the post-M2 backlog in `tasks/todo.md`. `SPEC.md` stays the source of truth; `spec/r0.md` and `spec/m2.md` stay the reference for what those milestones settled and are referenced, not copied. Deviations from `SPEC.md` are listed in §11 and each gets an ADR at `/ship`.

Status: **draft 2026-09-22, awaiting approval.** M2 shipped 2026-09-22 (`docs/ship/m2.md`). R0 criterion 8 (three mornings) closes on 2026-09-24; M3 may be planned before that and built after it.

---

## 1. Objective

Close the loop: the reader rates what the Editor chose, the Curator turns a week of ratings, reads and feed issues into proposals with evidence, and nothing about the profile changes until the reader approves a proposal on a page.

**User:** Duy, sole user. Taps 👍 or 👎 on an item and picks one reason, in one motion, on the phone. Once a week opens `/curator`, reads each proposal and its evidence, approves or rejects. Notices, the following week, that the digest moved.

**Two goals of equal weight** (`SPEC.md` preamble). Agent side: approval gates, hooks as a second-layer policy, proposal-with-evidence as the only way an agent changes state. Rust side: state machines as enums (`ProposalStatus`), one transactional `repo` call per approval, a second migration on a live database with a stated rollback.

**Done for M3** (`SPEC.md` §8 gate, restated as testable conditions in §9):
- ratings with reasons work on the phone and are stored; they change nothing else;
- the weekly Curator run produces proposals with evidence and writes nothing but proposal rows;
- approving a proposal applies it in one transaction; the first approved proposal changes the next exploit candidate list measurably;
- a `PreToolUse` hook refuses a malformed `propose_change` and the ninth web search before they reach the model's tools (or the fallback is documented, §12);
- every open item of the M2 review backlog has a named test and is closed or deferred with a reason.

**Out of scope for M3:** the Codex adapter (M4), `/stats` `/feeds` `/topics` and the systemd unit (M5), the own loop (M6), evals (M7), and the `seed` command (dropped, §11).

## 6. Code style

`spec/r0.md` §6 applies unchanged. M3-specific:

```rust
/// A proposal moves pending → approved | rejected exactly once; `approved` carries when and
/// what it applied. The enum is the state machine; the database column mirrors it.
#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize)]
#[serde(rename_all = "snake_case")]
pub enum ProposalStatus { Pending, Approved, Rejected }

/// What the Curator may propose (`SPEC.md` §5). Payloads are typed; unknown kinds never parse.
#[derive(Debug, Clone, PartialEq, Serialize, Deserialize, JsonSchema)]
#[serde(tag = "kind", content = "payload", rename_all = "snake_case")]
pub enum ProposalChange {
    TopicWeight { topic_id: String, weight: f32 },              // 0.1 ..= 5.0
    AddTopic { name: String, description: String, weight: f32 }, // description ≤ 200 chars, never leaves the service
    DisableSource { source_id: String },
    AddSource { url: String, title: String },                  // must have passed validate_feed in this run
    PromoteExploreTopic { topic_id: String },
}
```

- `apply(conn, &proposal)` is one function in `core::feedback`, called only by the approval route, inside one transaction that updates the target rows and sets the proposal `approved` with `applied_at`; a proposal whose target no longer exists is rejected by the same call with a reason.
- A rating row is `(item_id, digest_id, sign, reason, at)`; un-rating deletes it. No trigger, no side effect: the exploit scorer reads positive ratings as extra profile vectors within `candidate_days`; the Curator reads all of them.
- Tool listing is by role: the server built for a curator run lists exactly the five curator tools; an editor run never sees `propose_change` (a test proves both listings).
- The hook is pure: `hook::decide(tool: &str, input: &Value, state: &HookState) -> Decision`; the `dailybrief hook` verb wraps it with stdin/exit codes. The web-search counter lives in the run directory.
- Curator runs use the same runner, lock, attempts and transcript machinery as the Editor; `runs.role = 'curator'`; the day pages ignore curator runs; `/runs` shows the role.
- Digest page cap moves to 24 KiB (the rating widgets, §11); the run page keeps 64 KiB.

## 9. Success criteria (M3 gate, testable)

1. **Ratings.** Two taps on the phone (button, reason) store a `ratings` row; a second rating replaces it; the "un-rate" control deletes it. `SPEC.md` §6's reason set exactly. No other table changes (a test diffs row counts).
2. **Migration on the live database.** `dailybrief migrate` applies `0002_feedback` once; the R0 tables are byte-identical in content (row counts and a checksum of `items`, `digests`, `runs` before and after); the documented rollback SQL run on a copy restores the 0001 schema; the `m2` image serves the pages against a database that carries 0002 (rollback rehearsal).
3. **Curator writes only proposals.** One real `dailybrief curate` ends with ≥ 1 `proposals` row with non-empty evidence, `runs.role = 'curator'`, `scan-transcript` clean, and every other table's row count unchanged except `runs`/`run_events`.
4. **Approval moves the digest.** Approving a `topic_weight` proposal changes `topics.weight` in one transaction and the exploit top-80 list differs by ≥ 5 items before and after, proven on the seeded fixture; on the box, the morning after the first approval the `/runs/{id}` page of that run lists candidates from the changed profile (the run's `list_candidates` result differs from the previous morning's in ≥ 5 ids).
5. **Hook.** With hooks honoured under `--restricted` (§12): a `propose_change` with an unknown kind and the ninth `WebSearch` are refused before execution, visible as hook events in the transcript. If hooks are not honoured: the server-side refusal (`propose_change`) and the post-hoc scan (web search cap) are the documented layer, and the ADR says so.
6. **Weekly schedule.** The third schedule fires on Sundays at 07:30 local only (injected clock test); the first live Sunday run is recorded in the ship note.
7. **The M2 review backlog is closed by name**: `claude_binary_sha256_is_pinned`, `log_page_caps_events`, `pages_escape_planted_html`, `selects_count_accepted_selects_only`, `extracted_log_fires_after_dedupe`, `run_page_folds_once`, `stdout_line_size_is_bounded`, `orphaned_running_rows_are_marked_at_start`, `scan_transcript_accepts_run_id`, `ipv6_transition_ranges_are_private`, `jwks_forced_refetch_resumes_after_the_interval`, `retry_chain_respects_window_and_kind`, `extract_falls_back_when_primary_is_too_short`, `caps_wall_from_timestamps`, `prune_and_title_window_boundaries`, `prune_days_below_seven_is_refused_by_the_cli`, `run_status_ignores_a_stale_holder`, `fetch_sources_concurrent_with_barrier`; `readability` decided (ADR 0014 result).
8. **Gates.** `bin/check full` green in the container at the ship commit; CI green; coverage not below M2's; deploy between mornings with the image tagged first; rollback = `m2` tag plus the 0002 rollback note.

## 10. Boundaries

`spec/r0.md` §10 and `spec/m2.md` §10 apply in full. M3 adds:

**Always**
- Tag the running image before building (`runbook`), and run `dailybrief migrate` only from the new image, once, with the database backed up to a dated file in the volume first (`cp brief.db brief.db.pre-0002`).
- Keep the Curator's web searches to topic names (prompt) and the count to 8 (hook + scan).
- Treat rating rows as the reader's words: never edit or synthesise them; the Curator quotes them as evidence.

**Ask first**
- The one manual `curate` run and the first scheduled Sunday run (pre-approved, once each, 2026-09-22).
- Applying the migration on the live database (the deploy that carries it).
- Removing the TypeScript volumes.
- Any change to the reason set or the proposal kinds after `curator-tools` ships.

**Never**
- Let any code path other than `approval-web`'s `apply` write `topics.weight`, `topics.origin`, `sources.weight`, `sources.enabled`, or insert topics or sources (a test greps `repo` callers).
- Let a rating change anything but the `ratings` table.
- Send a topic description, a rating reason string with the reader's name, or anything but public article text and topic names to the model or the web (the egress scan gains the reason strings as allowed fragments and vault paths stay forbidden).
- Auto-approve, auto-apply, or apply on a timer.

## 11. Assumptions and deviations from SPEC.md

1. **Ratings only record** (approved 2026-09-22). `SPEC.md` §6's "immediate effect" column (item vector, saturation, source weight ±) is not implemented as state changes; positive ratings enter the exploit scorer as read-like profile vectors (a read of `ratings`, no write), and every weight or source change goes through a proposal. → ADR 0016.
2. **`seed` is dropped** (approved 2026-09-22): `config/topics.toml` is committed and hand-edited; `add_topic` proposals cover new topics. The ADR closes ADR 0010's deferral. → ADR 0017.
3. **`runs.role`** distinguishes curator runs; `runs.kind` keeps its CHECK. `0002_feedback` adds the column with default `'editor'`. The DDL and the rollback SQL are in ADR 0018.
4. **`find_feeds` takes a page URL**, not a topic: the service has no search backend; the model uses its `WebSearch` to find sites for a topic and then asks the service to discover feeds on a page. `SPEC.md` §5 writes `find_feeds({topic})`.
5. **Digest page cap 24 KiB** (was 15): two buttons and a reason list per item.
6. **Hooks under `--restricted`** are verified at the `curator-run` task; if `--settings` hooks do not fire, the hook stays in the repo as the policy for when they do, and the ADR records the fallback (§9 #5). → ADR 0019.
7. **Curator schedule Sunday 07:30 local**, third schedule in the one loop (no overlap with the morning run or the prune, which run first).
8. **Gate measure** "top-80 exploit list changes by ≥ 5 items" (approved 2026-09-22) is the definition of "measurably" in `SPEC.md` §8.
